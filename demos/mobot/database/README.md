# 모봇 7단계 공정 DB 개정안

## MySQL에 넣는 방법

이 초안은 MySQL 8.0.17 이상에서 실행할 수 있습니다. `mobot.dbml`은 전체 ERD를 보는 파일이며, 설치할 때는 `mobot.mysql.sql`을 실행합니다. SQL은 새 스키마 `moble_smart_factory_draft`에 테이블과 홈페이지 옵션 코드 8건을 만듭니다. 부품 연결값은 모두 `NULL`로 시작합니다.

1. Workbench에서 접속 가능한 계정으로 연결합니다. 같은 PC에서 설치할 때는 `127.0.0.1:3306`으로 연결할 수 있는 계정이 필요합니다. 제공된 계정은 루프백 로그인에서 `1045`가 반환됐고, 제공된 LAN 주소는 초기 응답이 시간 초과됐습니다.
2. 설치 계정에 새 스키마·테이블 생성과 초기 옵션 입력 권한이 있는지 확인합니다. `moble_smart_factory_draft` 이름이 비어 있을 때 Workbench에서 `File → Run SQL Script`로 `mobot.mysql.sql`을 실행합니다. 오류 시 실행을 중지합니다. 명령줄 대안은 아래와 같습니다.

```cmd
mysql --host=127.0.0.1 --port=3306 --user=YOUR_MYSQL_USER --password < mobot.mysql.sql
```

3. 새 스키마에 테이블 19개가 생겼는지 확인합니다. 생성이 중간에 실패한 경우 MySQL DDL은 이미 적용된 부분을 자동 롤백하지 않으므로 생성 범위를 확인합니다. 기존 `moble_smart_factory`는 이 초안의 설치 대상에서 제외합니다.

## 검토 자료와 DB 기준

- 첨부 텍스트의 DBML 9개 테이블, 로컬 `MOBOT.html`의 머리·왼팔·오른팔 선택값, `02_관제형.html`의 화면과 동작 코드, 팀 저장소의 로컬 협업·환경 설정 문서를 확인했습니다. 첨부된 dbdiagram 링크의 화면은 열리지 않았습니다. 관제형 HTML은 WPF 화면 시안으로, 주문과 장비 상태가 예시 값이며 로그인·제어 버튼도 브라우저 내에서 동작을 모의합니다.
- PC의 MySQL 서비스가 실행 중이며 설치 바이너리는 MySQL 8.2.0입니다. 실제 운영 스키마의 테이블, 서버 버전, 팀 운영 DB 선택은 로그인과 팀 확인이 필요합니다. 초안은 **MySQL을 단일 원본 DB**로 가정합니다.
- Raspberry Pi가 네트워크 단절 중에도 로그를 받아야 한다면 SQLite를 장비별 로컬 전송 대기열로 제한할 수 있습니다. Pi 게이트웨이가 명령·이벤트의 고유 ID를 보존해 재전송하고, 중앙 서비스가 MySQL에 커밋한 뒤 ACK를 돌려줍니다. Pi는 ACK가 확인된 이벤트를 대기열에서 정리합니다. 승인, 팔레트 배정, 레시피 발행과 최종 판정의 쓰기 권한은 중앙 서비스에 둡니다. 오프라인 운전 허용 여부와 큐의 재전송·보관 정책은 확인이 필요합니다.

## 기존 대비 변경사항

| 범위 | 변경과 이유 |
| --- | --- |
| 1단계 주문·배정 | `PARTS`, `WEB_PART_OPTIONS`, `LOCATIONS`를 추가했습니다. 주문 목적지, 2차 검사 배정 구역, AGV 실제 하역 구역을 같은 코드 마스터로 참조합니다. 공정 위치나 실제 장비 레일 번호와 코드의 대응은 설정에 둡니다. |
| 실행·팔레트 | `mapping_id`를 실행 ID로 사용합니다. 시작할 때 목표 부품 4개·목적지·레시피 버전을 고정합니다. `unmapped_at`에서 점유 여부를 생성하고, 점유 중인 팔레트와 주문에만 유일 키를 적용합니다. 실패·중단 뒤 회수 대기 중에도 팔레트 점유를 유지합니다. |
| 2단계 조립 | `(mapping_id, attempt_no)`로 조립 시도별 행을 남깁니다. `commanded_*`는 조립 명령에 선택된 부품이고 `*_motion_done`은 장비 동작 완료입니다. 자석 결합은 별도 확인 상태와 증거를 가집니다. |
| 3·5단계 검사 | 두 검사 모두 조립 시도에 연결하고 각 검사 테이블에서 `(mapping_id, attempt_no)`로 검사 차수를 관리합니다. 2차 검사에서 머리·왼팔·오른팔 각각의 검출 상태, 실제 ID, 신뢰도, 판정 사유를 저장합니다. 모델 일치 여부는 목표 스냅샷과 비교하고, 전체 `confidence_score`는 제거했습니다. |
| 4·6단계 이송 | AGV 센서 자체 정상, 팔레트 감지, 승강 목표 도달, 핸드셰이크를 분리했습니다. 각각 `NULL`은 미확인입니다. 계획 목적지와 확인된 실제 위치를 분리합니다. |
| 6·7단계 분류·회수 | `SORTING_RESULTS`는 실행당 최대 1건으로 실제 채택한 2차 검사와 성공한 하역 이력을 가리킵니다. 분류 결과와 배정 구역은 선택된 2차 검사에서, 실제 하역 구역은 AGV 이력에서 조회합니다. 회수 시각을 별도로 기록합니다. |
| 관리자·레시피 | 주문 진행과 승인 상태를 분리하고, 승인자·승인 시각·보류 사유를 기록합니다. 외부 인증의 발급자와 사용자 고유 ID에 관리자 역할을 연결합니다. 설정 변경, 승인·보류, 장비 조치는 `ADMIN_ACTION_LOGS`에 남깁니다. 레시피 버전과 순서가 있는 동작 단계를 분리했습니다. |
| 장비·경보 | 장비별 현재 운전 상태와 마지막 수신을 저장합니다. 명령과 주요 이벤트를 고유 ID로 식별하고, 경보에 장비·선택적 실행·해결 기록을 연결합니다. |

### 홈페이지 선택 코드와 DB 부품 ID

| 홈페이지 필드 | 선택값 | `PARTS.part_id` 대응 |
| --- | --- | --- |
| `head` | `dual` | 미확정. 첨부의 머리 ID 예시 `H1`, `H2`와 듀얼아이의 대응 확인 필요 |
| `head` | `mono` | 미확정. 첨부의 머리 ID 예시 `H1`, `H2`와 모노아이의 대응 확인 필요 |
| `left` / `right` | `grip` | 왼팔·오른팔 각각 미확정. 첨부에 그리퍼 계열이 있으나 정확한 ID 확인 필요 |
| `left` / `right` | `weld` | 왼팔·오른팔 각각 미확정. 첨부의 `L1`~`L4`, `R1`~`R4` 중 대응 확인 필요 |
| `left` / `right` | `fasten` | 왼팔·오른팔 각각 미확정. 첨부의 `L1`~`L4`, `R1`~`R4` 중 대응 확인 필요 |

`WEB_PART_OPTIONS`는 `(slot, option_code)`별 연결을 보관합니다. 서버가 구성 선택을 주문으로 변환하는 시점에 부위에 맞는 활성 부품 ID를 조회해 `ORDERS`에 저장합니다. 몸통 ID는 별도 제품 구성에서 가져옵니다. 기존 주문과 실행은 이미 저장된 ID를 조회합니다. 부품 ID의 의미가 바뀌면 새 ID를 등록하고 기존 ID는 비활성화합니다. 홈페이지 범위는 구성 선택 데모입니다.

## 무결성 및 서비스 검증 규칙

**MySQL에서 적용하는 제약**

- 실행의 주문·팔레트·레시피·목표 부품·목적지 FK는 필수입니다. 검사와 조립 시도, 2차 검사와 비교용 1차 검사, 최종 분류와 하역·검사 참조에는 복합 FK를 사용합니다. 특히 1차 비교 기준은 같은 실행의 같은 조립 시도여야 합니다. 검출 ID, 비교용 검사, 미확정 주문 목적지, 아직 없는 하역, 주문과 무관한 경보의 `mapping_id` 등에는 `NULL`을 허용합니다. FK에는 기본 삭제 제한을 사용합니다.
- 활성 키는 `CASE WHEN unmapped_at IS NULL THEN pallet_id/job_id END`입니다. 해제된 이력은 고유 인덱스에서 키가 `NULL`이라 여러 건이 유지됩니다. `ended_at`은 실행 종료, `unmapped_at`은 물리적 회수에 따른 점유 해제입니다. `is_active`는 쓰기 입력을 받지 않는 생성 열입니다.
- 검사 `NOT_RUN`은 미실시, `UNKNOWN`은 미확인·정보 없음, `UNDETERMINED`는 수행했으나 판정 불가를 뜻합니다. `ABSENT`는 관측으로 부품이 없음을 판정한 경우입니다. `IDENTIFIED`에만 실제 ID가 필요합니다. 신뢰도는 수신한 값만 0~1 범위로 기록하며 점수가 없으면 `NULL`입니다. 각도 `NULL`은 미측정이고 `0`은 측정값입니다. 검사 완료 행에 판정이 필요하며, `PASS`에는 해당 단계의 검출·QR 전제 조건이 필요합니다.
- 검사·조립·운반·명령의 종료 시각은 종료 상태일 때만 기록합니다. 실패·취소·중단 시각도 해당 상태와 `ended_at`의 조합으로 조회합니다. 검사 미실시 행에는 시작·종료 시각이 없습니다. 생성·발행 시각에만 현재 시각 기본값을 둡니다. 배포 시 서비스 연결의 시간대를 UTC로 맞추고 사용자 화면에서 한국 시간으로 표시합니다.
- 조회 인덱스는 주문 상태·승인·생성 시각, 주문/팔레트별 실행 이력, 실행별 시도 번호, 장비별 명령·경보·이벤트 시각, 경보 미해결 목록, 관리자·대상별 감사 이력을 기준으로 구성했습니다. FK 선두열 인덱스는 InnoDB가 필요에 따라 보완합니다.

**중앙 서비스에서 같은 트랜잭션으로 처리하는 규칙**

1. 배정 시 주문과 팔레트 행을 잠그고 생산 승인, 팔레트 `READY`, 활성 부품과 부위, 목적지 종류, 발행된 레시피를 검증합니다. 실행 스냅샷을 만들고 주문·팔레트 상태를 함께 갱신합니다. 배정 전 QR을 읽지 못했다면 팔레트 FK를 추측해서 만들지 않고 카메라 이벤트 또는 경보에 기록합니다. 팔레트가 이미 식별된 경우에만 실행 행의 QR 상태에 기록할 수 있습니다. QR과 몸통 사전 확인 조건은 조립 시작 전에 충족해야 합니다.
2. 시도 번호를 할당할 때 실행 행을 잠그고 이전 시도의 종료를 확인합니다. 새 시도는 새 행으로 추가하고 완료된 검사와 조립 이력을 동결합니다. 재조립 뒤의 검사는 새 조립 시도를 참조합니다. 검사기는 실행 목표·레시피 버전으로 실제 ID, 부위, 점수 기준과 각도 조건을 검증한 뒤 판정을 기록합니다. 오인식이나 기준 미달은 구체적 사유를 남깁니다. 전체 신뢰도가 UI에 필요해지면 계산 방식과 누락값 처리부터 버전별로 합의합니다.
3. 비교 검사로 탈락 정황을 관측하면 `SUSPECTED`와 1차 검사 참조를 기록하고, `CONFIRMED`는 확정 근거가 있을 때 사용합니다. `NO_EVIDENCE`는 확인 결과 탈락 증거가 없었다는 뜻입니다. 각도 측정과 자석 검증을 구현하지 않은 경우 미측정/미실시로 남깁니다. 레시피가 이를 필수로 정했다면 데이터가 없을 때 합격 처리할 수 없습니다.
4. 분류를 확정할 때 실행 행을 잠그고 최신 유효 조립 시도의 채택 가능한 종료 검사, 라우팅 규칙과 배정 구역을 확인합니다. `UNDETERMINED`를 재검사할지 `HOLD`로 처분할지는 정책으로 정합니다. 하역 성공 행을 연결할 때 `UNLOAD/COMPLETED`, 같은 실행, 계획 위치와 실제 위치, 시각 순서를 검증합니다. 위치가 다르면 실제 값을 유지하고 오류를 기록한 뒤 운영 규칙에 따라 처리합니다.
5. 정상 완료 또는 실패 후 회수에서 물리적으로 팔레트가 재사용 가능해졌을 때만 해제합니다. `unmapped_at`, 팔레트 `READY`, `cycle_count` 증가와 `updated_at` 갱신을 한 트랜잭션으로 처리합니다. 그 외 팔레트 상태 변경에도 `SET current_status = ?, updated_at = UTC_TIMESTAMP(6)`를 같은 트랜잭션에서 실행합니다. 타임아웃이나 장비 오류만으로 점유를 풀지 않습니다.
6. 관리자 역할 예시는 `OPERATOR`가 승인·보류와 경보 대응, `SUPER_ADMIN`이 추가로 역할 관리와 레시피 발행을 하는 방식입니다. 권한은 서버가 요청마다 검사합니다. 외부 인증을 사용하면 토큰 검증 뒤 `(auth_issuer, auth_subject)`로 계정을 찾습니다. 실제 인증 방식과 작업별 권한은 팀이 정합니다. 승인·보류·설정 변경은 대상 수정과 감사 기록을 같은 트랜잭션에 넣습니다.
7. 발행 시 레시피 설정과 동작 순서·좌표·단위·대상 장비를 검증합니다. 발행된 버전과 실행 스냅샷은 서비스에서 수정·삭제를 차단하고, 수정은 새 버전으로 발행합니다. 고정 사양이라면 레시피별 파일 경로·Git 커밋·내용 해시를 `RECIPE_VERSIONS.config`에 보관하고 해당 파일 버전을 계속 배포할 수 있게 유지합니다. 실행은 두 방식 모두 `recipe_version_id`로 추적합니다.
8. 명령은 `ISSUED → ACCEPTED → RUNNING → COMPLETED` 또는 실패·취소·중단으로 전이합니다. 재전송은 같은 `command_id`와 동일한 페이로드를 사용하고 실제로 새 동작을 승인한 경우 새 ID를 만듭니다. 게이트웨이와 장비도 같은 ID 재수신 시 기존 응답을 반환해야 합니다. 서비스는 늦은 응답이 종료 상태를 되돌리지 않도록 검증하고, 연결된 AGV 이력·이벤트의 장비와 실행이 원 명령과 일치하는지 확인합니다.

서비스 규칙에는 여러 행을 비교해야 하는 부위·시점·권한 검증과 이력 동결이 포함됩니다. SQL은 위의 단일 행 제약, FK, 유일 키를 설치하며 서비스 규칙의 실행은 앱·게이트웨이 구현에 포함됩니다.

### 실시간 화면과 영속 이력

`EQUIPMENT.run_state`는 장비의 `IDLE/RUNNING/PAUSED/ERROR/UNKNOWN`이며 주문 진행 상태와 독립입니다. `last_seen_at`과 설정된 타임아웃으로 연결 여부를 판단합니다. 수신 지연을 고려해 최신 수신 시각만 반영하고, 상태 전이와 간격을 둔 마지막 수신 갱신만 DB에 기록합니다. 고주기 센서값은 게이트웨이 메모리나 실시간 화면 스트림에서 처리합니다. 공정 진입·종료, 인터락 위반, 명령 응답, 연결 전이와 판정 증거처럼 재현에 필요한 데이터만 이력에 남깁니다.

## `02_관제형.html` 화면과 DB 연결

화면과 WPF 앱은 업무 서버에서 조회·조치를 요청하고, 업무 서버가 권한을 검사한 뒤 MySQL과 Pi 게이트웨이를 연결하는 구성을 제안합니다. 다음은 HTML의 실제 화면 요소를 기준으로 한 연결 설계입니다.

| 화면 | 조회·기록 방식 |
| --- | --- |
| 주문 대기열, 생산 승인·보류 | `ORDERS.status`, `approval_status`, `hold_reason`을 조회합니다. 승인·보류는 서버가 준비 상태와 권한을 확인한 뒤 `ORDERS`와 `ADMIN_ACTION_LOGS`에 기록합니다. 대기·진행 건수는 주문 상태에서 집계하고, **검사 보류** 건수는 실행의 현재 검사 판정과 분류 진행 상태에서 집계합니다. |
| 선택 주문과 공정 진행 | 선택 주문의 활성 `mapping_id`를 조회하고, 이력에서 선택한 경우 해당 실행을 명시합니다. 부품과 레시피 버전은 실행 스냅샷에서 조회합니다. `EQUIPMENT_EVENTS`에 주요 공정 진입·종료 이벤트와 `detail.stage_no`를 기록하는 방식을 제안합니다. 화면의 여섯 칸은 **주문·투입 → 정차·QR → 머리·팔 조립 → AGV 인계 → 비전 검사 → 목적지 이송**으로, DB 1~7단계와 번호를 공유하지 않습니다. 화면 상태는 주문 생성·사전 확인·조립·1차 검사·AGV 인계·2차 검사·하역·회수 이력으로 구성하고, 여섯 칸에서 1차 검사와 회수를 어떻게 표시할지는 확인이 필요합니다. |
| 주문 ↔ QR 대조 | 기대값은 실행의 `pallet_id`입니다. 실제 인식 문자열은 카메라의 `EQUIPMENT_EVENTS`에 `QR_READ` 이벤트로 남기고 `detail`에 `stage_no`, `read_status`, `scanned_qr`를 보관하는 방식을 제안합니다. 성공해서 읽은 값이 기대값과 다르면 불일치이고, 미수신·인식 실패·비교 대상 미지정을 별도로 표시합니다. 인식 문자열은 등록되지 않은 값도 들어오므로 FK를 걸지 않습니다. 실행 생성 전 이벤트는 `mapping_id=NULL`로 기록하며, 승인 전 기대 QR 표시와 주문에 그 스캔을 귀속할 방식은 운영 정책으로 확인해야 합니다. |
| 부품 대조·이미지·재검 요청 | 선택 실행의 목표 부품과 선택 검사 차수의 실제 부품 ID·검출 상태·신뢰도·사유를 표시합니다. 검사 이력은 `image_path`, `top_image_path`, `side_image_path`가 가리키는 이미지를 사용합니다. 실시간 영상은 카메라 스트림으로 수신합니다. 추가 카메라 두 칸은 위치·용도가 미정입니다. 재검 요청의 관리자 조치를 감사 이력에 남기고, 실제 검사 시작 시 새 `attempt_no`를 생성합니다. |
| 순환 팔레트·목적지 | `PALLETS`에서 QR·상태·순환 횟수·최종 변경 시각을 읽습니다. 주문 목표, 검사 배정, 실제 하역을 각각 조회해 현재 단계에 맞는 값을 표시합니다. `ORD-023`의 불량 구역 예시는 주문 목표로 시드하지 않습니다. |
| 설비 연결·최근 이벤트·확인 필요 | 장비별 `last_seen_at`과 `run_state`, `EQUIPMENT_EVENTS`, 미해결 `ALARM_LOGS`를 사용합니다. 왼팔 미검출 등 검사 보류는 검사 결과에서도 조회합니다. 화면의 온도·AGV 배터리·IR은 수신할 수 있을 때 실시간 상태로 표시하고, 임계치 위반이나 상태 전이만 이력으로 기록합니다. |
| 일시정지·재개·소프트웨어 정지·컨베이어 정지 요청 | 소프트웨어 제어를 구현할 때는 대상 컨트롤러와 `EQUIPMENT_COMMANDS`의 요청·접수·완료·실패를 연결합니다. 화면에 요청 상태를 먼저 표시하고, 장비의 정지 피드백 이벤트가 들어온 뒤 확인 상태를 표시합니다. 라인 운전 상태는 컨트롤러가 보고한 상태에서 조회합니다. 로그인 전에도 보이는 컨베이어 버튼의 실제 권한, 물리적 정지·복귀 방식 및 피드백은 설비 담당자 확인이 필요합니다. |
| 최상위 관리 설정·로봇 좌표 | `ADMIN_ACCOUNTS`, `ADMIN_ACTION_LOGS`, `RECIPE_VERSIONS`, `RECIPE_STEPS`를 사용합니다. 현재 위치 기억·RELEASE·순서 시험은 시안에서 비활성화돼 있습니다. 구현 시 서버에서 권한과 정비 모드를 확인하고, 조작 이력과 발행된 레시피 변경을 추적합니다. |

QR 원문과 공정 이벤트에는 기존 `EQUIPMENT_EVENTS.detail`을 사용하므로 이 대조에서 테이블을 추가할 필요가 없었습니다. 예시 주문은 공통 팔 코드 `A1`/`A2`, 수량 1개를 사용합니다. 실제 좌우 부품 매핑과 주문 수량 정책은 팀 확인 사항입니다.

## 기록 예시

아래 ID와 판정은 흐름을 설명하기 위한 예시입니다. 실제 부품·구역·레일 ID는 팀 확인이 필요합니다.

| 시나리오 | 주요 기록 |
| --- | --- |
| 정상 주문 | `J1` 승인 → `M101`에 `P1`과 레시피 v1 고정 → 조립 1차 `COMPLETED` → 1차 검사 `PASS` → AGV `TAKEOVER` → 2차 `I201/PASS`, 배정 `ZONE-A` → 분류가 `I201` 참조 → AGV `UNLOAD`에서 실제 `ZONE-A` 확인 → 회수와 함께 실행 종료 및 점유 해제. |
| 재검사·재조립 | `M102`의 2차 검사 1회 `UNDETERMINED`와 흐림 사유를 남기고 2회 `PASS`를 새 행에 저장. 분류는 2회만 참조. 재조립했다면 조립 시도 2번을 추가하고 이후 검사는 그 시도를 참조. |
| 팔레트 재사용 | `M101` 해제 후 `P1`을 `J3/M103`에 연결. `M101`과 이후 종료한 여러 실행이 이력으로 남고 활성 키는 현재 실행에만 생김. |
| 중복 배정 | `M103`이 `P1`을 점유할 때 다른 주문의 `P1` 배정, 또는 `J3`의 다른 팔레트 배정을 시도하면 각각 고유 인덱스가 거절. 서비스는 트랜잭션을 롤백하고 기존 점유를 표시. |
| 장비 오류 | 명령 `C402`가 `FAILED`, 장비 `AGV-X`가 `ERROR`, `ALARM_LOGS`에 `M103`을 연결. 실패 실행은 종료 시각을 갖되 회수 전까지 점유를 유지. 관리자 해결 시 조치자·시각·내용을 기록. 유휴 장비의 경보는 `mapping_id=NULL` 가능. |

## 최종 확정 질문

1. 팀의 중앙 운영 DB는 MySQL인가요? SQLite를 쓰면 Pi 오프라인 버퍼 용도인가요? 오프라인 운전을 허용하는 공정과 재전송 책임자는 누구인가요?
2. `dual`, `mono`, 좌우 각각의 `grip`, `weld`, `fasten`에 대응하는 실물 ID는 무엇인가요? 몸통 ID 및 홈페이지에 없는 팔 종류의 사용 범위는 어떻게 되나요?
3. 목적지는 머리 종류에서 결정하나요, 주문에서 선택하나요? 정상·보류·불량·회수 구역의 코드와 실제 레일·스테이션 번호는 무엇인가요?
4. 주문 하나는 제품 1대·활성 팔레트 1개인가요? 병렬 생산·부분 수량·실패 후 동일 주문 재실행이 있다면 그 단위와 팔레트 점유 해제 기준은 무엇인가요?
5. 1차 검사에서 불합격이 나면 재조립·재검사·즉시 분류 중 무엇을 하나요? 재시도 한도, 2차 보류/불량 판정, 저신뢰 기준, 최종 검사 채택 조건은 무엇인가요?
6. 기울기·측면 각도·자석 결합을 실제로 측정하거나 검증하나요? 운반 중 탈락을 확정할 증거는 무엇인가요? 19.2 mm, RF 핸드셰이크, 오류 레일 번호가 확정값인가요?
7. 외부 인증 제공자와 1차·최상위 관리자의 실제 권한은 무엇인가요? 로그인 화면의 컨베이어 정지 요청은 운영에서도 노출하나요? 정지·복귀의 제어 주체와 상태 확인 신호는 무엇인가요?
8. 레시피를 DB에서 편집·발행할지 버전 고정 파일을 배포할지 정해졌나요? 로봇 좌표계·단위와 장비별 명령 응답/고유 ID, 연결 타임아웃은 무엇인가요?
9. 기존 스키마에 유지해야 할 데이터가 있나요? 있다면 미확인 성공 기본값과 기존 완료 시각을 판별할 원본 증거, 마이그레이션 및 팀 검증 담당자는 누구인가요?
10. 승인 전에 기대 팔레트 QR을 지정하나요? 시안의 6칸에 1차 검사와 팔레트 회수를 어떻게 표시하나요? 추가 카메라 2개의 용도는 무엇인가요?
