# 단계 승격과 버전 태그

| 단계 | 의미 | 번호 | 시작 예시 |
| --- | --- | --- | --- |
| Alpha | 초안·화면·기능 구현 | `0.0.xV` | `0.0.1V` |
| Beta | 1차 뼈대·주요 흐름 검토 | `0.x.xV`, 두 번째 숫자 1 이상 | `0.1.0V` |
| Release | 필요한 오류 수정과 해당 버전 검증 완료 | `1.x.xV` | `1.0.0V` |

태그 이름에 공백을 쓰지 않고 대문자 V로 끝냅니다. 앞에 v를 추가하지 않습니다.
Alpha 마지막 번호는 9에서 10으로 계속 증가하며 숫자 자릿수만으로 Beta로 승격하지 않습니다.
Beta는 예를 들어 `0.1.0V → 0.1.1V → 0.2.0V`, Release는 `1.0.0V → 1.0.1V → 1.1.0V`처럼 관리합니다.
구체적인 다음 번호와 버전 범위는 관리자가 정합니다.

## 단계 승격

1. 관리자가 해당 버전의 포함 범위와 검증 근거를 확인합니다.
2. Alpha에서 Beta로, Beta에서 Release로 PR을 엽니다.
3. 현재 base/head와 필수 검사, 실제 제품 검증을 확인하고 Merge commit으로 병합합니다.
4. 요청된 버전이라면 대상 브랜치에 반영된 검증 커밋에 Annotated 태그를 만들고 정확한 태그 하나를 push합니다.
5. 배포가 필요한 경우 그 태그의 GitHub Release에 실행 파일·변경 내역·실행 조건을 연결합니다.

Alpha·Beta·Release는 유지하는 장기 브랜치이며 단계 간 승격을 Squash·Rebase하지 않습니다.
초기 협업 파일을 세 브랜치에 준비한 것과 제품의 성숙 단계는 구분합니다. 초기 설정에는 버전 태그를 만들지 않습니다.
OWNER Esp3ra는 일반 push 예외가 있지만 단계 간 PR 승격은 Merge commit 원칙을 따릅니다.
초기 공통 설정을 같은 기준으로 맞출 때는 이력을 보존하는 fast-forward를 사용할 수 있습니다.

## 안정화·긴급 수정의 역반영

Beta에서 고친 오류는 필요한 경우 Alpha에도 반영하고, Release의 긴급 수정은 Beta·Alpha에도 반영합니다.
먼저 수정 브랜치에서 해당 단계로 PR을 제출합니다. 이어 관리자가 역반영 범위를 검토하고 단계 간 Merge commit PR로 연결합니다.
관리자가 지정한 수정 브랜치 접두어는 `fix/`, `hotfix/`, `docs/`, `chore/`, `test/`를 사용할 수 있습니다.

## 태그 예시

아래는 관리자가 Release의 배포 대상 커밋과 검증을 확인한 뒤 실행하는 예시입니다.
이미 존재하는 이름을 다시 사용하지 않습니다.

```powershell
git fetch origin --tags
git switch Release
git pull --ff-only origin Release
# 이번 버전의 제품 빌드·테스트·필수 환경 확인을 완료한 뒤:
git tag -a 1.0.0V -m "Release 1.0.0V"
git show 1.0.0V
git push origin 1.0.0V
```

태그는 브랜치별 별도 이름 공간이 아닙니다. 저장소 전체에서 유일한 이름입니다.
GitHub Actions의 태그 검사도 이름·Annotated 여부·해당 단계 이력 포함 여부를 확인하지만,
태그 생성 이후 수행되는 검사이므로 실제 제품 검증과 올바른 대상 커밋 확인을 대신하지 않습니다.
