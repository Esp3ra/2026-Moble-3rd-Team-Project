# 컨베이어·AGV 실장비 혼합시험

이 모드는 미구현 조립·YOLO 대신 대역을 사용해 메인 서버와 WPF의 실제 연결을 검증한다.
공통 통신규약 v0.3.0의 API·DTO·장비 명령·완료 이벤트 형식은 그대로 사용한다.
운영용 조립·검사 합격이나 전체 장비 검증을 증명하지 않는다.

| 구간 | 연결 |
| --- | --- |
| WPF·업무 서버·명령 outbox·완료 기록 | 실제 제품 코드 |
| LINE·액추에이터·IR1·IR2 | 실제 LINE HTTP 연결 모듈과 장비 |
| CAM1 QR | 실제 카메라·ROI 판독·팔레트 배정 |
| ARM 조립·CAM2 좌표 갱신 | 규약을 따르는 SimDevice·좌표 대역 |
| YOLO 검사 | 모의 PASS, `MIXED_TRIAL_SIMULATED` 모델·보정 ID |
| AGV 인수·배송·하역·복귀 | 실제 AGV HTTP 연결 모듈과 ESP32 |

## 준비

서버·어댑터를 종료하고 실물의 진행 중 동작과 미확정 명령을 먼저 대조한다.
운영 기록의 복구를 회피하려고 새 시험 journal을 만들면 안 된다.
AGV는 실제 2번·지게 85°·정차·자동 모드여야 하며 다른 웹/파이썬 제어 연결은 종료한다.
모터 배터리·컨베이어·액추에이터 전원을 준비하고 배송 경로와 하역 공간을 확인한다.

`server/mobot`에서 다음 예시를 실행한다. Python은 제품 가상환경을 사용한다.
실제 인증값은 프로젝트 밖 설정 파일에만 보관한다.

```powershell
python -B scripts/prepare_mixed_trial.py --directory "$env:LOCALAPPDATA\MOBOT\mixed-trial" --admin-login EXISTING_LOGIN
scripts/Start-Mixed-Trial.ps1 -Directory "$env:LOCALAPPDATA\MOBOT\mixed-trial"
```

AGV를 실제 2번에 배치했고 지게 85°이며, 정지 후 위치 재등록이 필요하면
시작 명령에 `-ConfirmedStandbyAt2`를 추가한다. 이는 작업자의 실물 확인에 근거한 위치 등록이며 자동 감지가 아니다.

준비 스크립트는 새 디렉터리만 허용한다. 기존 LINE/AGV 접속 설정과 CAM1 ROI를 복사하고,
지정한 관리자 한 명의 로그인·암호 해시만 새 DB에 등록한다. 주문·세션·검사·진행 기록은 복사하지 않는다.
일반 운전에는 이 설정을 사용하지 않는다. `MOBOT_MIXED_TRIAL=1`과 시험 프로필이 둘 다 있어야 하며,
DB의 `MIXED_TRIAL` 범위를 일반 HARDWARE·SIMULATION DB로 다시 사용할 수 없다.
기존 커스텀 운영 DB에도 범위 검사를 적용해 덮어쓰기를 차단한다.
시험 프로필의 AGV 전체 명령 제한은 최소 90초의 임시 시험값이며, 요청별 HTTP 제한과 분리한다.
최종 시간값은 실제 인수·배송·하역·복귀 측정 후 확정한다.

실제 실행은 기존 `app.py`와 `device_adapter.py`·`agv_client.py`를 사용한다. 혼합시험 실행기가 로컬 어댑터의 수명을 관리하며,
메인 서버는 계속 표준 `/device/v1` HTTP와 완료 이벤트로 동작한다. 메인 서버 8000과 설정된 AGV 어댑터 포트를
기존 프로세스가 사용하면 시작을 중단한다. LINE 터널·이벤트 callback·인증은 이 시험 서버를 가리켜야 한다.
LINE이 이전 부팅의 이벤트를 보내거나 결과를 알 수 없는 동작을 가진 경우 정상 준비로 간주하지 않는다.
시험 프로필의 LINE은 `controller_keepalive_seconds: 0.2`로 독립적인 표준 상태 GET을 보낸다.
AGV의 느린 응답이나 영상 처리 때문에 LINE의 짧은 서버 제어권 기한이 만료되지 않도록 한다.
이 경로도 매번 서버 DB 제어권을 확인하며 이동·배출 명령을 재전송하지 않는다.
AGV 상태 GET의 소켓 오류는 한 번만 새로 조회한다. 잘못된 응답·인증 오류와 두 번 연속 실패는 정상으로 숨기지 않는다.
이동·지게 등 POST 동작은 이 재조회 대상이 아니다. 장치 완료·부팅·제어권 확인은 그대로 유지한다.
`agv-transport.jsonl`에는 요청 종류·대기/응답 시간·오류 종류·상태 값만 별도 스레드에서 기록한다.
인증키·URL·명령 파라미터는 남기지 않는다. 상태 재조회 보완만으로 근본적인 네트워크 지연 해결을 보장하지 않는다.

## WPF에서 3·4·5번 시험

1. 새로 빌드한 WPF에서 `http://127.0.0.1:8000`에 로그인한다.
2. 상단의 **실장비 혼합시험 · LINE/AGV 실물 · 조립/YOLO 모의** 표시와 혼합시험 탭을 확인한다.
3. LINE·AGV 연결, 실제 CAM1 QR 영상과 팔레트 배출 위치를 확인한다. 준비 실패 시 시작 버튼은 비활성화된다.
4. 목적지 **3번 서울 / 4번 대전 / 5번 천안**을 고르고 **선택 목적지로 실장비 시험 시작**을 누른다.
5. 버튼은 기존 `POST /orders` → 주문 수락 → `POST /plant/actions START`를 사용한다.
   각 단계는 고정한 요청 UUID로 중복 제거한다. 응답 유실 시 같은 목적지·요청을 조회/확인하며 새 이동을 재전송하지 않는다.
6. 액추에이터 배출 → IR1 실제 정차 → CAM1 QR 배정 → 모의 조립·검사 저장 → IR2 실제 정차 →
   `PICK_UP` → `DELIVER` → `UNLOAD` → `RETURN_STANDBY` 순서와 주문 이력을 확인한다.
7. AGV의 명령 ID·위치·지게 실제 완료가 확인되어야 서버가 다음 단계로 진행한다.
   완료 후 자동 시작은 꺼진다. 각 시험에는 READY 상태의 서로 다른 팔레트를 사용한다.
   하역한 팔레트는 `AWAIT_MANUAL_RETURN`으로 남으며 자동으로 READY 처리하지 않는다.

전체 공정 정지·정지 해제는 기존 WPF 버튼과 규약을 사용한다. 통신 단절·부팅 변경·미확정 결과는
기존 복구 대기 조건을 유지한다. 실패한 명령을 성공으로 바꾸거나 journal을 삭제하지 않는다.

### 활성 회차가 없는 대기 복구 버튼

혼합시험 탭의 확인란은 작업자가 **AGV 실제 2번·무적재, 컨베이어·액추에이터 정지, 컨베이어 비움**을
직접 확인했다는 뜻이다. 확인 후 **현장 확인 후 대기 복구**를 누른다.
기존 `ManualRequest`/`ManualResult`와 `/api/v1/manual-actions`를 사용하며,
고정 절차 `AGV_IDLE_STANDBY_RECOVERY_V1`만 이 시험 프로필에 등록한다. 운영 모드에는 활성화되지 않는다.

LINE이 온라인 IDLE이고 활성 회차·자동운전·미완료 동작 명령이 없어야 실행한다.
LINE 자체의 USB·서버 연결 고장은 먼저 복구해야 한다. 주행 중 주문이 남은 경우 이 버튼으로 정상 처리할 수 없다.
서버는 시험 시작을 차단한 채 같은 AGV journal과 로컬 연결 모듈을 인계하고, 멈춘 장치에서 지게 85°와
작업자 확인 위치 2번을 한 번 등록한다. 모의 ARM만 재시작하고 실제 LINE·AGV가 IDLE인지 재확인한다.
이전 불확정 PAUSE/RESUME만 STOPPED로 끝내고, 완료 이벤트나 검사 합격은 만들지 않는다.
이전 주문·장비 명령·journal은 보존하고 작업자·사유·복구 요청 ID를 감사 기록에 남긴다.
자동운전은 꺼진 상태로 유지한다. 카메라 등이 미준비면 복구 후에도 NOT_READY이며 시작할 수 없다.
응답 유실은 같은 요청 ID와 결과 조회로 확인한다. 서버 재시작 중 복구는 UNKNOWN으로 남기고 자동 재실행하지 않는다.
장치의 비공개 설정을 가진 로컬 작업자는 시작 명령의 `-ConfirmedStandbyAt2 -RecoverIdleStandby`로
같은 등록 절차를 명시적으로 요청할 수 있다. 이 경우 감사 주체는 `LOCAL_OPERATOR`이며 웹 관리자 세션을 만들지 않는다.

## 검증 범위

`test_mixed_trial.py`는 격리 DB·비구동 장비 대역·실제 AGV 어댑터 HTTP로 3·4·5번 흐름,
IR2 전 인수 차단, 저장된 모의 검사 ID 전달, 별도 DB 범위·옵트인을 확인한다.
WPF 회귀시험은 목적지·기존 API 사용·응답 유실 시 동일 UUID와 목적지 유지·운영 모드 버튼 차단을 확인한다.
이 자동검사는 실물 성공을 뜻하지 않는다. 각 목적지 실물 시험과 오류·정지 시험 결과는 별도로 기록한다.

기존 [하드웨어 공정](HARDWARE_WORKFLOW.md)과 [통합 시험표](../tests/integration/SCENARIOS.md)를 함께 검토한다.
PR은 혼합시험임을 명시하고 실제 시험한 장비·목적지·코드 버전과 모의 범위를 구분한다.
