## 팀원 초대

현재 팀원 계정은 미정입니다. 관리자가 계정을 확인한 뒤 저장소의 Settings → Collaborators에서
작업 브랜치를 push할 수 있는 공동작업자로 초대하고, 팀원이 초대를 수락합니다.
개인 계정 소유 저장소의 공동작업자와 조직 저장소의 역할 체계는 다를 수 있으므로 실제 권한을 확인합니다.
읽기 권한만으로는 작업 브랜치를 올릴 수 없습니다. 권한이 없을 때 포크로 우회하지 않습니다.

## GitHub·Codex를 처음 사용하는 팀원

1. GitHub 계정을 관리자에게 전달하고 이 저장소의 공동작업자 초대를 수락합니다.
2. PC에 Git과 Codex를 준비하고 로그인합니다. 인증·설치가 막히면 Codex에 현재 상황을 적어 직접 해야 할 단계만 안내받습니다. 비밀번호·토큰은 채팅에 보내지 않습니다.
3. Codex에서 프로젝트 폴더를 작업 위치로 선택합니다. 아직 저장소를 받지 않았다면 다운로드할 새 폴더·빈 폴더를 정하고, 아래 프롬프트의 폴더 항목에 적습니다.
4. [팀원용 프롬프트](prompts/codex-github-member-prompt.txt)의 본문을 복사하고 대괄호 항목을 채워 보냅니다. 파일 경로나 용어를 모르면 '모름'과 맡은 기능을 쉬운 말로 적어도 됩니다.
5. Codex가 준비·구현·검증·제출을 진행합니다. 권한이나 담당 합의처럼 본인이 결정해야 할 내용만 답하고, 제출된 PR 링크로 관리자 검토를 받습니다.
6. 수정 요청을 받으면 같은 채팅에 Issue 번호·PR 링크와 수정 요청을 전달합니다. 기존 PR을 갱신하며 팀원이 Merge하거나 검토 Issue를 먼저 닫지 않습니다.

작업 브랜치는 변경을 모으는 작업 공간, 커밋은 변경 기록, push는 GitHub 업로드, PR은 관리자에게 검토·반영을 요청하는 항목입니다. Alpha에서 개발하고 Beta·Release 승격과 버전 태그는 관리자가 담당합니다.

### 같은 채팅의 다음 요청

전체 프롬프트는 첫 시작 때 한 번만 사용합니다. 이후에는 달라진 정보와 다음 양식만 보내면 됩니다. 새 채팅을 시작하거나 역할·담당이 바뀌면 해당 프롬프트와 변경된 정보를 다시 전달합니다.

```text
작업 유형: 구현·PR 제출 / 설명·검토만
할 일: [원하는 변경]
완료 조건: [확인할 동작]
관련 PR·Issue: [있으면 링크, 없으면 없음]
```

환경 설정이 막혀도 같은 작업이 가능한 부분은 이어갑니다. 실행할 수 없는 필수 검사 때문에 Draft PR을 제출했다면 사유를 확인하고 관리자와 후속 검증을 진행합니다.

## 기본 작업 순서

1. 같은 저장소를 clone하고 최신 Alpha를 받습니다.
2. PR로 검토할 작업 묶음마다 `feature/이름-작업`, `fix/이름-작업`, `docs/이름-작업`, `chore/작업`, `test/작업`, `refactor/작업` 브랜치를 만듭니다. 파일·수정마다 만들지 않고 보통 1인당 진행 중인 작업 하나를 유지합니다.
3. 담당 범위의 구현과 관련 문서를 수정하고 필요한 검증을 수행합니다.
4. 필요한 파일만 커밋·push하고 같은 저장소의 Alpha를 base로 PR을 제출합니다.
5. 관리자가 전체 변경과 검증 근거를 검토합니다. PR에서 필요한 수정·회신을 이어갑니다.
6. 검증 조건을 충족하면 관리자가 병합하고, 아래 확인을 거쳐 해당 작업 브랜치를 삭제합니다. 병합 요청에는 이 정리가 포함되므로 별도 삭제 승인을 반복해서 묻지 않습니다.

### 병합 후 작업 브랜치 정리

- 관리자는 PR의 실제 병합 완료와 변경 반영을 확인합니다. Squash 병합은 조상 관계만으로 판단하지 않습니다.
- 현재 원격 head가 병합 당시 커밋과 같고 미반영 변경·추가 커밋이 없으며, 해당 브랜치를 head 또는 base로 참조하는 다른 Open PR이 없는지 확인한 뒤 삭제합니다. SHA가 바뀌거나 남은 작업이 있으면 보류하고 보고합니다.
- 삭제 후 원격 브랜치가 사라졌는지 확인합니다. 로컬본은 미커밋 변경을 보존하고 기준 브랜치로 전환한 뒤 정리합니다. 다른 팀원의 PC는 해당 팀원이 확인합니다.
- `main`·`Alpha`·`Beta`·`Release`는 계속 유지하며 승격·역반영 PR의 출발점이어도 삭제하지 않습니다. 병합하지 않고 닫은 PR은 이 기본 삭제 대상이 아닙니다.
- GitHub에서 관리자가 직접 병합한 경우에도 같은 확인 후 PR의 Delete branch로 단기 작업 브랜치를 삭제합니다. 저장소 전체 자동 삭제는 사용하지 않습니다.

팀원은 브랜치에 push하고 PR을 열 수 있으며, 단계 브랜치의 최종 병합은 Esp3ra가 담당합니다.
Beta 안정화·Release 긴급 수정은 관리자가 명시적으로 맡긴 경우에만 해당 단계에서 시작합니다.

OWNER `Esp3ra`는 예외로 main·Alpha·Beta·Release에 PR 없이 일반 push할 수 있습니다.
이 예외는 Esp3ra 계정에만 적용하며 다른 공동작업자에게 적용하지 않습니다.
직접 push에는 사전 PR·필수 CI 조건이 적용되지 않지만 push 후 정책 CI는 계속 실행됩니다.
강제 push·기준 브랜치 삭제와 기존 태그의 이동·삭제 차단은 OWNER에게도 적용합니다.

## PR 리뷰 우선, 별도 추적은 Issue

현재 PR에서 해결할 오류·수정 요청은 코드 위치와 완료 조건을 **PR 리뷰**에 남깁니다.
병합을 막는 문제도 수정 요청·병합 보류로 표시하고, 작업자가 **같은 브랜치·PR**을 수정해 재검토받습니다.
Issue 생성 기준은 심각도보다 **이 PR 밖에서도 계속 추적할 필요가 있는지**입니다.

| 상황 | 처리 |
| --- | --- |
| 오타·특정 코드 수정, 이 PR에서 끝나는 오류 | PR 리뷰·수정 요청 |
| 기존 버그·여러 담당자나 PR에 걸친 문제·후속 기능 | 일반 Issue와 관련 PR 연결 |
| 별도 추적이 필요하고 한 PR의 병합으로 완료되는 검토 요청 | 예외적으로 `pr-review` 검토 Issue |

### 일반 버그·기능·후속 작업

[일반 Issue 양식](https://github.com/Esp3ra/2026-Moble-3rd-Team-Project/issues/new?template=work_item.yml)을 사용합니다.
중복을 확인하고 담당자·문제나 목표·영향 범위·완료 조건·목표 브랜치·관련 PR을 적습니다.
아직 PR이 없어도 등록할 수 있으며 모든 작업에 사전 Issue를 강제하지는 않습니다. PR에는 `Refs #이슈번호`나 링크로 연결합니다.

일반 Issue에는 `pr-review` 라벨을 붙이지 않습니다. 관련 PR 하나가 Merge되었다는 이유만으로 닫지 않고,
관리자가 목표 브랜치에서 모든 완료 조건을 확인한 뒤 종료합니다.
예를 들어 Release 버그를 Alpha에만 반영했거나 다른 PR·실제 환경 검증이 남으면 Open으로 유지합니다.

### 한 PR에서 완료되는 검토 Issue

[검토 Issue 양식](https://github.com/Esp3ra/2026-Moble-3rd-Team-Project/issues/new?template=pr_review.yml)은
일반 리뷰보다 별도 추적이 필요하면서 **지정한 한 PR의 병합으로 완료되는 경우**에만 사용합니다.

1. `pr-review` 라벨과 **관련 PR** 항목에 같은 저장소의 PR URL 또는 `#번호` 하나만 적습니다.
2. 문제·재현 조건·파일 위치·완료 조건은 별도 `###` 항목에 쓰고 PR에 `Refs #이슈번호`나 링크를 남깁니다.
3. 작업자는 같은 PR을 갱신하고 리뷰·연결된 Issue에 수정 커밋과 검증 결과를 회신합니다.
4. 관리자는 완료 조건·최신 PR 커밋·필수 CI·미해결 리뷰를 재확인하고, 추가 변경을 재검토한 뒤 병합합니다.
5. 자동화는 해당 PR과 연결된 Open `pr-review` Issue만 Closed(completed) 처리합니다. 관리자는 Actions와 실제 종료를 확인합니다.

수정 push만 했거나 PR을 Merge 없이 닫았다면 자동 종료하지 않습니다. 일반 Issue·다른 PR의 Issue도 제외합니다.
Issue의 일반 PR 언급만으로 자동 종료되지 않으며 전용 **관련 PR** 항목을 사용합니다.
목표가 여러 PR·단계 검증으로 커지면 관리자가 일반 Issue로 전환하고 `pr-review` 라벨을 제거합니다.

Open Issue 자체가 Merge 버튼을 막지는 않습니다. 미해결 리뷰는 관리자가 수정 요청·병합 보류로 관리합니다.
문제 기록만을 위한 문서·브랜치는 만들지 않습니다.
GitHub의 `Closes #번호`는 기본 브랜치 대상 PR에 적용되므로, Alpha·Beta·Release의 검토 Issue에는 전용 자동화를 사용합니다.
실패하면 Actions의 **Close merged PR review issues**를 확인합니다. 수동 실행 기본값은 dry run이며,
실제 재처리는 PR 번호와 `dry_run=false`로 실행합니다. 자동화는 main 코드만 실행하고 PR head는 실행하지 않습니다.
OWNER 직접 push에는 Merge 이벤트가 없으므로 완료 확인 후 관리자가 관련 Issue를 수동 종료합니다.

## 원격 보호 설정

초기 설정 작업은 다음 규칙을 GitHub에 적용하고 실제 적용 결과를 별도로 확인합니다.
문서만으로 적용 완료를 판단하지 않습니다.

- `main`, `Alpha`, `Beta`, `Release`: 팀원은 PR과 `repository-policy` 검사 통과 필요, 미해결 리뷰 대화 해결 필요.
- 위 브랜치: 업데이트는 Esp3ra만 가능하며 OWNER는 직접 일반 push 또는 PR 병합을 사용할 수 있습니다.
- 강제 push·삭제는 별도 규칙에서 우회 계정 없이 차단하여 OWNER 일반 push 예외와 분리합니다.
- `Beta`, `Release`: PR 승격은 Merge commit을 사용합니다. 팀원 대상 규칙은 Merge commit만 허용하고 OWNER 일반 push는 예외로 처리합니다.
- 버전 태그: 관리자만 생성하고, 생성된 태그의 이동·삭제를 차단합니다.
- 별도 사람 승인 수는 초기에는 요구하지 않습니다. 관리자 본인 PR의 자기 승인 불가로 진행이 막히지 않게 하되, 관리자 검토와 CI 조건은 유지합니다.
- 저장소 전체의 자동 브랜치 삭제는 사용하지 않습니다. 관리자가 PR 병합 후 해당 단기 작업 브랜치를 확인·삭제하고 네 기준 브랜치는 보존합니다.

일반 협업은 PR의 변경·검증 결과를 확인한 관리자가 병합하는 흐름입니다.
OWNER가 직접 반영할 때도 실제 검증이 빠져 있다면 통과했다고 표현하지 않습니다.

## CI가 확인하는 범위

`repository-policy`는 같은 저장소에서 만든 PR인지, 대상 단계와 출발 브랜치가 허용되는지,
필수 협업 파일이 있는지, 실제 비밀정보·DB·생성 산출물이 추적되는지와 diff 공백 오류를 확인합니다.
정책 검사 코드의 회귀 검사도 함께 실행합니다.

제품 소스가 아직 없으므로 앱 빌드·동작·공유 서버·DB·장치 검사는 수행하지 않습니다.
제품 코드 도입 시 해당 기술 스택에 맞는 빌드·테스트 CI를 같은 PR에서 추가합니다.

## 기본 브랜치 main

main은 저장소 안내·공통 협업 설정을 유지합니다. 제품 기능은 Alpha로 제출합니다.
main의 안내·설정 변경은 `docs/` 또는 `chore/` 작업 브랜치에서 PR을 제출하고 관리자 검토를 받습니다.
공통 설정이 다른 유지 브랜치에서도 필요한 경우 해당 브랜치로 반영하는 PR을 준비합니다.
