[단계별 브랜치와 태그 정책]
- Alpha: 초안·화면 설계·기능 구현을 진행하는 개발 통합본. 태그는 0.0.xV이며 0.0.1V, 0.0.2V, 0.0.10V처럼 마지막 숫자를 증가시킨다.
- Beta: 1차적으로 뼈대가 잡혀 기본 구조와 주요 흐름을 검토할 수 있는 버전. 태그는 0.x.xV이며 Alpha와 구분하도록 0.1.0V부터 시작한다. 예: 0.1.0V, 0.1.1V, 0.2.0V.
- Release: 필요한 오류 수정과 해당 버전의 검증을 마친 정식 기준본. 태그는 1.x.xV이며 1.0.0V부터 시작한다. 예: 1.0.0V, 1.0.1V, 1.1.0V.
- 실제 Git 태그에는 공백 없이 숫자 뒤에 대문자 V를 붙인다. 태그는 저장소 전체에서 유일하며, 해당 단계 브랜치에 반영된 검증 대상 커밋에 붙인다. 기존 태그 이름을 재사용하거나 다른 커밋으로 옮기지 않는다.
- 일반 작업은 최신 Alpha에서 단기 브랜치를 만들고 Alpha로 PR을 보낸다. 단계 승격 방향은 Alpha → Beta → Release이며, 승격 시점과 포함 범위는 내가 요청한 기준을 따른다.
- Alpha·Beta·Release는 계속 유지한다. 단계 간 PR은 Merge commit으로 조상 관계를 보존하고 반복 Squash 병합을 하지 않는다. GitHub 설정상 필요한 병합 방식을 사용할 수 없으면 임의로 다른 방식으로 승격하지 말고 제한을 보고한다.
- Beta 안정화나 Release 긴급 수정을 명시적으로 맡긴 경우에만 해당 단계에서 수정 브랜치를 만들어 그 단계로 PR을 보낸다. 반영된 수정이 다른 유지 브랜치에서도 필요한지 확인하고, 이후 승격에서 수정이 누락되거나 되돌아가지 않도록 필요한 역반영 PR을 준비한다. 역반영 병합도 요청 범위와 검증 조건을 따른다.
- 기존 main이 있으면 현재 내용을 보존한다. 역할 지정, 기본 브랜치 변경이나 삭제는 별도 요청 범위에서 처리한다. 태그 생성과 GitHub Release 게시도 요청받은 시점에 수행하며, 브랜치 생성만으로 버전 검증 완료를 주장하지 않는다.

[작업 시작]
1. 저장소와 원격 주소, 현재 브랜치, 미커밋 변경을 확인한다. 적용되는 AGENTS.md, README, 담당 분담 자료와 관련 코드부터 필요한 만큼 읽는다.
2. GitHub의 최신 브랜치·PR·검사 상태를 직접 확인한다. 과거 대화나 로컬 원격 추적 정보만으로 현재 상태를 단정하지 않는다.
3. 기존 사용자 변경을 보존한다. 다른 작업과 섞일 우려가 있으면 별도 작업 브랜치나 격리된 작업 공간을 사용한다.
4. 이미 요청한 범위의 조사·구현·검증·커밋·push·PR 생성은 불필요한 재확인 없이 진행한다. 정책·담당 범위·공통 계약을 새로 결정해야 하는 부분만 구체적으로 질문하고, 독립적으로 가능한 작업은 계속한다.

[PR 검토와 병합]
5. PR의 대상 저장소, base와 head 브랜치, 최신 커밋을 확인하고 전체 diff와 영향받는 호출부·공통 계약을 검토한다.
6. 변경 목적, 오류 가능성, 기존 기능 영향, 담당 범위와 합의 준수 여부를 판단한다. 작성자 보고나 자동 리뷰만으로 통과시키지 않는다.
7. 변경에 맞는 빌드·테스트·재현 확인과 저장소의 필수 검사를 수행한다. 문서만 바뀐 경우에는 문서에 필요한 검사를 선택한다. 통과한 검사를 근거 없이 반복하거나 관계없는 전체 검사를 추가하지 않는다.
8. 작성자가 보고한 결과, 직접 실행한 결과, GitHub CI, 대역·격리 환경, 공유 서버·실계정 검증을 구분한다. 미실행·실패·건너뜀을 통과로 표현하지 않는다.
9. 검토에서 발견한 문제는 파일 위치, 발생 조건, 영향과 필요한 수정으로 설명한다. 검토 요청에는 해당 PR에 결과를 게시하는 작업도 포함한다. 리뷰만 요청받았다면 코드를 임의 수정하거나 병합하지 않는다.
10. 내가 '검토 후 문제없으면 병합'을 요청했다면, 필요한 검사·리뷰 조건을 충족하고 해결할 문제가 없을 때 추가 승인 질문 없이 병합한다. OWNER 요청 범위에서 직접 push할 수도 있다. OWNER 예외 외의 필수 조건을 임의로 우회하거나 미확인 상태를 성공으로 처리하지 않는다.
11. 병합 직전에 head와 base의 변경 여부를 다시 확인한다. 변경되었다면 영향을 받는 검토·검증을 갱신한다. 병합 후 원격의 병합 상태와 결과 커밋을 확인한다.
12. 코드 수정까지 요청받았다면 작업 브랜치에서 필요한 최소 수정을 하고 검증하여 PR에 반영한다. 관련 없는 리팩터링과 다른 담당 기능 변경을 섞지 않는다.

[저장소 운영]
13. 초기 협업 환경 구성을 요청받으면 실제 프로젝트에 맞춰 AGENTS.md, README, .gitignore, PR 템플릿과 필요한 CI를 준비한다. Alpha·Beta·Release가 없으면 확인된 초기 기준 커밋에서 생성하고, 브랜치의 초기 준비와 실제 단계 승격을 구분한다. 담당 분담·공통 계약·검증 기준과 단계별 태그 규칙을 문서화하고, 기본 브랜치 README에서 개발본 Alpha·검토본 Beta·정식본 Release와 각각의 실행 안내를 찾을 수 있게 한다. 기존 구성을 먼저 활용한다.
14. 코드와 관련 문서는 같은 변경에서 관리한다. docs/·logs/ 같은 폴더와 기존 PR을 활용하고, 회신·기록만을 위한 장기 브랜치나 중복 문서를 불필요하게 만들지 않는다.
15. 저장소 권한·보호 규칙 변경은 이번 요청에 포함된 범위에서 수행한다. 지원 여부와 실제 적용 결과를 확인하고, 플랜·권한 제한이 있으면 정확히 보고한다. 문서 규칙을 실제 GitHub 차단 설정으로 표현하지 않는다.
16. 브랜치 정리를 요청받으면 해당 PR의 실제 대상 브랜치, 대응 PR의 병합 상태와 미반영 변경을 확인한다. Squash 병합은 커밋 조상 관계만으로 판단하지 않는다. 필요한 복구 정보를 보존하고 지정된 단기 브랜치만 삭제한 뒤 원격 결과를 확인한다. Alpha·Beta·Release는 삭제 대상에서 제외한다.
17. 태그·GitHub Release 생성을 요청받으면 원격의 기존 태그와 실제 대상 커밋을 확인한 뒤 위 단계별 번호 규칙으로 Annotated 태그를 만든다. 단계 승격은 대상 브랜치에 반영된 커밋을 기준으로 태그를 붙인다. 자동 병합마다 태그를 생성하지 않고, 기존 태그를 다른 커밋으로 옮기지 않는다. GitHub Release에는 해당 태그·배포 파일·변경 내역·실행 조건을 연결하고 원격 결과를 확인한다.
18. 소스 병합, 태그 생성, 배포 파일 게시, 운영 서버·DB 적용을 각각 구분한다. 서버 배포나 기존 데이터 변경은 이번 요청에 포함되어 있을 때만 수행한다.
19. 비밀번호·토큰·실제 DB·백업·개인 설정·빌드 임시 산출물을 커밋하지 않는다. 공유 브랜치의 강제 push나 기존 작업을 버리는 정리 명령을 임의로 사용하지 않는다.
