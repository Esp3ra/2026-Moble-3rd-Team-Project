[협업과 버전]
- 포크 없이 같은 저장소에서 협업한다. 팀원은 작업별 단기 브랜치에서 Alpha로 PR을 보낸다.
- Alpha: 초안·기능 구현. 태그는 0.0.xV (예: 0.0.1V).
- Beta: 1차 뼈대·주요 흐름 검토. 태그는 0.x.xV이며 0.1.0V부터 시작한다.
- Release: 오류 수정과 해당 버전의 검증을 마친 정식본. 태그는 1.x.xV (예: 1.0.0V).
- main은 저장소 안내용이다. 단계 승격은 Alpha → Beta → Release이며 PR 승격은 Merge commit을 사용한다.
- OWNER Esp3ra는 main·Alpha·Beta·Release에 PR 없이 일반 push할 수 있다. 팀원에게 이 예외를 적용하지 않는다.
- 강제 push·단계 브랜치 삭제·기존 태그 이동과 삭제는 OWNER도 하지 않는다.

[작업 원칙]
1. 적용되는 AGENTS.md와 관련 문서를 읽고 실제 Git 루트·원격·브랜치·미커밋 변경 및 최신 GitHub 상태를 확인한다. 다른 차수 프로젝트와 기존 사용자 변경을 보존한다.
2. 요청한 범위의 조사·수정·검증·커밋·push·PR 처리를 끝까지 진행한다. 이미 허용된 작업은 반복 확인하지 않고, 필요한 정책·공통 계약 결정만 질문하며 독립 작업은 계속한다.
3. PR은 전체 diff와 관련 호출부·계약·담당 범위를 검토한다. 관계없는 기능 수정과 리팩터링을 섞지 않는다. 병합 차단 문제는 기존 Issue를 확인하고 pr-review 검토 Issue로 기록한다. 본문 '### 관련 PR' 항목에 해당 PR URL 또는 #번호 하나와 문제·재현 조건·수정 완료 조건을 적고 PR에도 연결한다. 기록용 문서·브랜치는 만들지 않는다.
4. 변경에 필요한 검증만 수행한다. 직접 확인한 결과, 작성자 보고, CI와 미실행 항목을 정확히 구분한다. 같은 검사를 근거 없이 반복하지 않는다.
5. 검토만 요청받으면 결과를 해당 PR에 정리하고 미해결 문제는 병합 보류한다. 작업자가 같은 PR을 갱신하면 수정 조건을 재검토하고, 병합을 요청받은 범위에서 추가 승인 없이 병합한다. 연결된 검토 Issue는 Merge 후 자동 종료되므로 수정 push만으로 닫지 않는다. OWNER 직접 반영은 요청 범위에서 사용하고 push 후 CI와 관련 Issue의 완료를 별도로 확인한다.
6. 코드와 관련 문서는 함께 관리한다. 담당자 합의 없이 공개 API·DTO·DB 스키마·권한 정책을 바꾸지 않는다. 비밀정보·실제 DB·백업·개인 설정·빌드 산출물을 게시하지 않는다.
7. 브랜치 정리는 요청받은 단기 브랜치만 병합 상태와 미반영 변경을 확인한 뒤 수행한다. Squash 병합은 커밋 조상 관계만으로 판단하지 않는다.
8. 태그·GitHub Release·운영 적용은 요청받은 범위에서 수행한다. 태그는 해당 단계의 검증된 커밋에 공백 없는 Annotated 태그로 만들고 같은 이름을 재사용하지 않는다.
