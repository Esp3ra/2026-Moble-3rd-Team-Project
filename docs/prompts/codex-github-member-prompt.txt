[협업과 버전]
- 포크 없이 팀 저장소에 작업 브랜치를 push하고 같은 저장소의 Alpha로 PR을 제출한다.
- Alpha는 초안·기능 구현(0.0.xV), Beta는 1차 뼈대 검토(0.x.xV, 0.1.0V부터), Release는 오류 수정·검증을 마친 정식본(1.x.xV)이다.
- 단계 승격·태그·배포는 관리자가 처리한다. OWNER Esp3ra의 직접 push 예외는 팀원에게 적용되지 않는다.

[작업 원칙]
1. 적용되는 AGENTS.md와 관련 문서를 읽고 Git 루트·원격·브랜치·미커밋 변경·기존 PR과 최신 Alpha를 확인한다. 기존 사용자 변경을 보존한다.
2. 최신 Alpha에서 feature/이름-작업, fix/이름-작업, docs/이름-작업 같은 단기 브랜치를 만든다. 같은 작업의 열린 PR이 있으면 갱신하고, 병합된 작업 브랜치를 새 작업에 재사용하지 않는다.
3. main·Alpha·Beta·Release에 직접 커밋·push하지 않는다. 관리자가 별도 단계의 안정화·긴급 수정을 맡긴 경우에만 해당 단계에서 작업 브랜치를 만들어 지정된 단계로 PR을 보낸다.
4. 담당 범위와 합의된 계약을 지켜 구현한다. 다른 담당의 구현이나 공개 API·DTO·DB 스키마·권한 정책을 임의로 바꾸지 않는다. 공통 변경이 필요하면 이유와 최소 변경안을 정리하고 독립 작업은 계속한다.
5. 변경에 필요한 검증만 수행하고 실제 결과와 미실행 항목을 구분한다. 대역·격리 환경 결과를 공유 서버·실계정 검증으로 표현하지 않는다.
6. 제출 전에 전체 diff와 최신 기준의 충돌을 확인한다. 필요한 파일만 선택해 커밋하고 비밀정보·실제 DB·백업·개인 설정·빌드 산출물을 제외한다.
7. 이번 요청은 담당 작업의 구현·검증·커밋·push·PR 생성을 허용한다. 완료되면 추가 확인 없이 PR을 제출한다. 미완료나 필수 검증 미실행 사항이 있으면 Draft로 제출하고 사유를 적는다.
8. PR에는 문제와 변경 후 동작, 담당 범위, 실제 검증 결과, 미실행 항목, 필요한 설정과 공통 계약 영향을 간결하게 쓴다. 검토 Issue를 받으면 내용을 확인하고 같은 작업 브랜치와 PR에 수정한다. PR에 Issue 링크를 연결하고 Issue 댓글에 수정 커밋·확인 결과를 남긴다. Issue는 관리자의 Merge 후 자동 종료되므로 직접 닫거나 회신용 문서·브랜치를 만들지 않는다. 모든 작업에 사전 Issue 생성을 강제하지 않는다.
9. 팀 저장소 쓰기 권한이 없으면 필요한 권한을 안내하고 가능한 로컬 작업을 계속한다. 포크로 우회하지 않는다. 자신의 PR을 병합하거나 다른 팀원의 브랜치·PR·저장소 설정을 임의로 변경하지 않는다.
