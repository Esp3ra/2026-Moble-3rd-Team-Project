아래 담당 범위에서 구현·검증·커밋·push·PR 생성까지 완료하라.

- 협업 방식: 포크 없이 팀 저장소 안의 작업 브랜치에서 PR 제출

[팀의 단계별 브랜치와 태그 정책]
- Alpha: 초안·화면 설계·기능 구현을 진행하는 개발 통합본. 태그 형식은 0.0.xV (예: 0.0.1V, 0.0.2V).
- Beta: 1차적으로 뼈대가 잡혀 기본 구조와 주요 흐름을 검토할 수 있는 버전. 태그 형식은 0.x.xV이며 0.1.0V부터 시작한다 (예: 0.1.0V, 0.1.1V).
- Release: 필요한 오류 수정과 해당 버전의 검증을 마친 정식 기준본. 태그 형식은 1.x.xV (예: 1.0.0V, 1.0.1V).
- 태그 이름은 공백 없이 대문자 V로 끝낸다. Alpha → Beta → Release 승격, 태그 생성과 GitHub Release 게시는 관리자가 처리한다. 브랜치 이름만으로 실제 검증·배포 완료를 주장하지 않는다.
- 일반 작업 PR은 Alpha로 제출한다. 관리자가 Beta 안정화나 Release 긴급 수정을 명시적으로 맡긴 경우에만 해당 단계에서 수정 브랜치를 만들고 지정된 단계로 PR을 보낸다. 다른 단계로 반영할 필요가 있는 수정은 PR에 명시한다.

[작업 시작과 브랜치]
1. 적용되는 AGENTS.md, README, 담당 분담·공통 계약과 관련 코드를 확인한다. 저장소 원격 주소, 현재 브랜치, 미커밋 변경과 기존 PR도 확인한다.
2. GitHub의 최신 Alpha를 받아 작업한다. 신규 일반 작업은 최신 Alpha에서 feature/이름-작업, fix/이름-작업, docs/이름-작업 같은 단기 브랜치를 만든다. 별도로 지정된 단계 수정은 해당 단계의 최신 기준에서 만든다. Alpha가 없으면 main 등 다른 브랜치를 임의로 통합 기준으로 삼지 말고 관리자에게 초기 준비가 필요함을 알린다.
3. 같은 작업의 진행 중인 브랜치·PR이 있으면 그것을 이어서 사용한다. 이전 작업의 병합이 끝난 브랜치에 새 기능을 계속 쌓거나 같은 목적의 PR을 중복 생성하지 않는다.
4. 개인 포크를 만들거나 사용하지 않는다. 원격이 팀 저장소인지와 작업 브랜치 push 권한을 확인하고, 팀 저장소의 작업 브랜치에서 같은 저장소의 통합 브랜치로 PR을 만든다. 쓰기 권한이 없으면 포크로 우회하지 말고 관리자에게 필요한 권한을 안내한다. 가능한 로컬 구현·검증은 계속한다.
5. 기존 사용자 변경을 보존하고 이번 작업과 섞지 않는다. main·Alpha·Beta·Release에는 직접 커밋·push하지 않는다. 작업용 단기 브랜치만 사용한다.

[구현과 협업 범위]
6. 내 담당 범위와 합의된 계약을 지켜 필요한 변경을 끝까지 구현한다. 기존 구조·스타일을 활용하고 관계없는 최적화·리팩터링을 섞지 않는다.
7. 다른 담당 코드를 읽고 연동을 확인할 수는 있지만, 합의 없이 그 담당의 구현이나 공개 API·DTO·DB 스키마·권한 정책을 바꾸지 않는다.
8. 공통 변경이 필요하면 필요한 이유, 영향받는 파일·계약, 최소 변경안을 정리해 해당 부분만 확인을 요청한다. 독립적으로 가능한 구현·검증은 계속한다. 다른 담당의 기능 전체를 대신 구현하지 않는다.
9. 요청한 기능이 실제 사용자 흐름에서 이어지는지 확인한다. 임시 데이터나 대역으로 확인한 범위와 실제 서버·DB에 연결한 범위를 구분한다.

[검증과 PR 제출]
10. 변경에 맞는 빌드·테스트·오류 재현 확인과 저장소 필수 검사를 수행한다. 오류 수정에는 필요할 때 회귀 검증을 추가한다. 문서 변경에는 문서에 맞는 검사를 수행한다.
11. 필요한 검사가 통과하면 제출로 진행한다. 새 변경이나 실패·미해결 우려가 없는데 검사를 반복하거나 검증 범위를 계속 넓히지 않는다.
12. 제출 전에 최신 통합 기준과 비교하여 이번 작업만 포함되는지 전체 diff를 확인한다. 기준 브랜치와의 충돌은 의미를 확인하며 해결하고 영향받는 검증을 갱신한다. 해결 과정에서 다른 사람의 변경을 버리지 않는다.
13. 비밀번호·토큰·실제 DB·백업·개인 설정·bin/obj 등 임시 산출물을 제외한다. 내가 수정한 필요한 파일만 선택해 목적이 드러나는 커밋을 만든다.
14. 이번 요청은 작업 브랜치의 커밋·push와 PR 생성을 허용한다. 필요한 검증이 끝났다면 추가 확인 없이 지정된 통합 브랜치로 PR을 만든다. 작업이 미완료이거나 필수 검증이 남았다면 Draft PR로 제출하고 이유를 적는다.
15. PR에는 해결한 문제와 동작 변화, 담당 범위, 검증 명령·환경·결과, 미실행 항목, 공통 계약·DB 영향, 필요한 설정을 간결하게 쓴다. 관련 Issue가 있으면 연결하고, 제출 후 대상 저장소·base/head·최신 커밋을 확인한다.
16. 리뷰 수정 요청을 받으면 같은 작업 브랜치와 PR에 반영하고 영향받는 부분을 다시 검증한다. 변경에 따른 PR 설명과 검증 결과도 갱신한다.
17. 다른 팀원의 브랜치·PR을 임의 수정하거나 병합하지 않는다. 자신의 PR도 직접 병합하지 않는다. 저장소 설정·보호 규칙·배포·태그·Release·공유 브랜치 삭제는 관리자가 처리하도록 남긴다. 강제 push로 공유 이력을 덮어쓰지 않는다.

[최종 보고]
한국어로 구현한 내용, 작업 브랜치와 커밋, PR 링크와 대상 브랜치, 실행한 검증, 미완료·차단 사항을 짧게 보고한다. PR 제출을 원본 병합이나 운영 배포 완료로 표현하지 않는다.
