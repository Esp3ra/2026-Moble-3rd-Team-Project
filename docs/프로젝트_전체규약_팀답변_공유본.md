이해준과의 문답 및 제공 시험 코드 검토를 정리한 팀 공유 자료다. **문답으로 결정한 요구사항, 현재 확인한 구현, 미정 사항을 구분한다. 요구사항 결정은 구현·실차 검증 완료를 뜻하지 않는다.**

## 번호별 질문과 답변

### 01. 팔 부품의 좌우 호환

**질문:** 같은 팔 부품을 왼쪽·오른쪽에 모두 끼울 수 있나요?

**팀 답변** 전부 공용. 모든 팔 부품은 좌우 구분 없이 왼팔·오른팔에 공통으로 사용한다.

### 02. 제품 목록과 부품 코드

**질문:** 실제로 만들 머리와 팔의 종류, 선택할 수 없는 조합은 무엇인가요?

**팀 답변 — 최신 공통 명칭 확정**

구매 웹·DB·YOLO 라벨에 아래 명칭을 공통으로 사용하기로 한다.

| 구분 | 실물 종류 | 구매 웹·DB·YOLO 공통 명칭 | 실물 보유 수량 |
| --- | --- | --- | --- |
| 머리 | 듀얼아이 | `H1` | 4개 |
| 머리 | 모노아이(적외선) | `H2` | 4개 |
| 팔 | 집기팔 | 왼쪽집기 `L1` / 오른쪽집기 `R1` | 총 8개(좌우 공용 재고) |
| 팔 | 용접팔 | 왼쪽용접 `L2` / 오른쪽용접 `R2` | 총 8개(좌우 공용 재고) |
| 팔 | 나사팔 | 왼쪽나사 `L3` / 오른쪽나사 `R3` | 총 8개(좌우 공용 재고) |
| 몸통 | 공용 몸통 | 별도 명칭 미확정 | 8개 |

- 이 결정으로 앞서 사용하던 머리 A/B, 왼팔 a/b/c, 오른팔 1/2/3 기준을 대체한다.
- 좌우 팔의 명칭은 구분하지만 실제 부품은 종류별로 좌우 공용이다. 같은 종류를 양쪽에 선택하면 해당 공용 재고에서 2개를 차감한다.
- 주문 조합은 머리 2종 × 왼팔 3종 × 오른팔 3종 = 총 18가지이다.
- 로봇팔이 집을 부품은 종류별 고정 공급 위치에 배치한다. 구체적인 공급·조립 좌표와 보정 기준은 미정이다(14번).
- YOLO 라벨은 H1/H2/L1/L2/L3/R1/R2/R3으로 정한다. 좌우 공용 부품의 영상상 좌우 판정·학습 기준은 미정이다(16번).
- 이는 최신 명칭 결정이다. 실제 구매 웹 소스·DB 데이터·YOLO 라벨 파일 및 모델의 변경 완료를 확인한 것은 아니다. 각 담당자는 기존 자료를 이 기준으로 통일해야 한다.

### 03. 품절과 주문 변경

**질문:** 부품이 부족하거나 주문 사양을 바꾸려면 어떻게 처리할까요?

**팀 답변**

- 각 부품의 재고는 DB로 관리한다.
- 부품 재고가 부족해지면 관리자에게 알린다.
- 구매 웹은 DB 재고에 따라 품절을 표시하고, 부족한 부품이 필요한 주문을 받지 않는 방향으로 운영한다.
- DB 재고 부족 시 주문 단계에서 품절로 처리하며, 제작 중 부품 부족을 별도 정상 공정 분기로 두지 않는다.
- 재입고 기능을 요구사항에 추가한다. 관리자 화면에서 부품별 입고 수량을 등록해 DB 재고에 가산하고 구매 웹의 품절 표시를 재고와 연동한다. 실제 구현 완료를 의미하지 않는다.
- 관리자의 제작 승인 전 주문 사양을 변경하려면 기존 주문을 취소하고 재주문한다.
- 구매 웹에서 주문이 접수되는 즉시 해당 주문에 필요한 부품 재고를 차감한다.
- 소비자가 수락 전에 취소하거나 관리자가 배출 전 대기 주문을 취소하면 차감 재고를 한 번 복구한다. 입고 수량 등록은 최상위 관리자 권한이다.
- 같은 종류의 팔을 왼쪽과 오른쪽에 모두 선택하면 해당 종류의 공용 팔 재고에서 2개를 차감한다.

### 04. 구매 웹 범위

**질문:** 소비자는 어떻게 주문·본인 확인을 하고, 어디까지 진행 상태를 볼까요?

**팀 답변**

- 소비자 구매 웹은 회원가입·로그인 기능 없이 운영한다.
- 소비자는 본인의 주문번호로 주문 내역과 진행 상태를 조회하는 방식으로 계획한다.
- 주문번호 조회 기능은 현재 미구현이다.
- 별도 확인코드 도입은 확정하지 않았다.
- 신용카드·계좌이체를 선택하고 버튼을 누르는 모의 결제가 구매 웹에 구현되어 있다. 실제 금전 결제는 수행하지 않는다.
- 구매 웹에서 회사명·전화번호·전체 주소를 입력받을 계획이다.
- 고객이 입력한 전체 주소의 지역을 분류해 배송 HUB를 자동 배정한다. 단순히 서울·평택·수원 세 단어의 포함 여부만으로 분류하지 않는다.

| 주소의 배송 지역 | 배정 HUB | AGV 목적지 |
| --- | --- | --- |
| 서울·인천·경기·강원·제주 | 서울 HUB | 3번 |
| 충청·전라·대전·세종·광주 | 수원 HUB | 5번 |
| 경상·부산·대구·울산 | 평택 HUB | 4번 |

- 고객이 HUB를 직접 고르는 대신 위 주소 권역에 따라 자동 배정한다.
- 고객 주문 조회 화면의 정상 진행 상태는 접수 → 제작 중 → 검사 중 → 배송 중 → 허브 도착의 5단계로 표시한다.

### 05. 팔레트 재사용

**질문:** 팔레트는 몇 장이고, 하역한 팔레트는 누가 어떻게 타워로 되돌리나요?

**팀 답변**

- 사용할 실물 팔레트는 총 8개이다.
- 팔레트 식별자는 PALLET-01, PALLET-02, PALLET-03, PALLET-04, PALLET-05, PALLET-06, PALLET-07, PALLET-08이다.
- 사용자가 제공한 8개 PNG를 직접 QR 판독한 결과, 각 이미지에 해당 팔레트 ID 문자열 1개가 들어 있고 모두 파일명과 일치했다. 이미지 파일 8개 준비는 확인했다.
- 사용자가 PALLET-01~PALLET-08의 QR을 실물 팔레트 8개에 부착했고 DB 등록도 완료했다고 확인했다. 이는 사용자 확인 사항이며, 문답 중 실제 DB 접속이나 현장 카메라 시험을 수행한 것은 아니다.
- 하역한 제품과 팔레트는 사람이 수동으로 회수한다. 제품을 회수한 뒤 팔레트를 타워에 다시 쌓아 재사용한다.
- 팔레트 회수 자동화 기능은 이번 구현 범위에 포함하지 않는다.
- 소프트웨어가 회수를 감지해 재사용 가능 상태를 자동 확정하는 기능은 확정하지 않았다. 실제 재적재는 작업자가 수행한다.
- 실물 팔레트 ID와 생산 회차 ID는 분리한다(10번).

### 06. 재검·재조립

**질문:** 6번이나 7번에 하역한 제품을 누가 확인하고 어디서 다시 투입하나요?

**팀 답변**

- 오류로 분류해 6번 또는 7번에 하역한 제품은 우선 해당 오류 구역에 그대로 둔다.
- 이번 구현 범위에는 오류 제품의 재검·재조립 요청 및 재투입 기능을 포함하지 않는다.
- 오류 제품의 후속 회수·처리 및 재투입 절차는 현재 확정하지 않는다.

기존 공정 기준의 오류 분류는 유지한다.

| 목적지 | 오류 기준 |
| --- | --- |
| 6번 · 오류1 | 확인된 필수 부품 누락. QR 오류가 동시에 발생해도 누락을 우선한다. |
| 7번 · 오류2 | 누락이 확인되지 않은 나머지 오류. 오부품·QR 불일치/미인식·영상 가림에 따른 판정 불가 등을 포함한다. |

### 07. 통합 DB

**질문:** 최종 시연 DB는 SQLite와 MySQL 중 무엇으로 하고, 기준 스키마는 누가 관리할까요?

**팀 답변**

- 최종 시연의 통합 DB는 SQLite를 사용한다.
- 기존에 공유한 시스템 구성도 기준으로 구매 웹·관리자 WPF는 메인 PC의 업무 서버/API에 연결되고, 통합 SQLite DB는 업무 서버에 연결하는 구조로 설계한다.
- DB에는 주문·팔레트·검사·이송 이력을 관리한다. 이 답변은 구성도상의 설계 기준이며 실제 연동 구현 완료를 의미하지 않는다.
- DB 테이블 구조(기준 스키마)와 변경 사항은 최종현·함동윤이 관리한다. 두 담당자의 주담당·대체 담당 구분은 별도로 확정하지 않았다.

### 08. 연결 방식

**질문:** 웹·WPF·Pi·AGV·UNO가 어떤 방식으로 명령과 상태를 주고받을까요?

**채택 기준 · 연결과 책임**

- 기존 시스템 구성도와 대화에서 확인된 연결 관계를 따른다.
  - 구매 웹·관리자 WPF → 메인 PC 업무 서버/API → SQLite DB.
  - 메인 PC → 현장 Raspberry Pi → Arduino UNO → 컨베이어·액추에이터·IR 센서 등 현장 소자.
  - 메인 PC → 로봇팔 제어용 Raspberry Pi(myCobot 280 Pi).
  - 메인 PC → ESP32 AGV.
  - QR 등록·로봇팔 좌표 보정·암실 QR/YOLO 검사·전체 모니터링 카메라 4개는 모두 메인 PC에 연결한다.
- AGV 연결 모듈이 ESP32의 HTTP 제어 세션·하트비트·상태 조회를 공통 명령·이벤트로 변환한다. 기존 WebSocket은 공통 필수 인터페이스에 포함하지 않는다.
- 웹·WPF는 메인 PC의 HTTPS JSON API를 호출한다. 서버는 장비 명령을 보내며, 장비 연결 모듈은 완료 이벤트를 회신한다. 메인 PC 안의 비전은 같은 DTO를 함수로 전달한다.
- 현장 Pi↔UNO는 USB 시리얼 115200 bps·8N1·ASCII 줄 단위 v1 전문을 채택했다. 기존 시험 펌웨어에는 새 전문을 구현하고 검증해야 한다.

### 09. DTO와 공통 메서드

**질문:** 어떤 필드·메서드·상태 이름을 팀 공통으로 정하고 어디에 명세를 둘까요?

**채택 기준 · DTO와 메서드**

- 메인 서버는 `/api/v1`, 장비 연결 모듈은 `/device/v1`을 사용한다. 경로별 메서드명, 권한, 필수·선택 필드, 오류·완료 응답은 [OpenAPI](통신규약/openapi.yaml)를 따른다.
- JSON은 snake_case, 서버 시각은 UTC, WPF 표시는 한국 시각을 사용한다. 장비의 명령 접수와 실제 완료는 별도 응답으로 기록한다.
- 기준 문서는 GitHub main/docs/통신규약에서 관리한다. 장비별 시간과 물리 허용오차는 실물 시험 후 보완한다.
- 소비자 조회 화면의 확정 표시 상태는 04번을 따르며, 이를 장비 공통 상태 코드와 동일한 것으로 간주하지 않는다.

### 10. 작업 번호와 중복 처리

**질문:** 같은 요청을 두 번 받거나 예전 팔레트 회신이 늦게 도착하면 어떻게 구분할까요?

**팀 답변 — 운영·구현 원칙 확정**

- 주문·실물 팔레트·생산 회차·장비 명령·검사를 각각 별도 ID로 관리한다.
- 같은 명령을 중복 수신해도 실물 동작은 한 번만 실행한다. 이미 접수된 명령의 처리 상태 또는 기존 결과를 확인할 수 있게 한다.
- 실물 팔레트 ID와 생산 회차 ID를 분리해 동일 팔레트를 재사용해도 서로 다른 생산 작업을 구분한다.
- WPF 수락 순번 등 기존 확정 공정 기준을 따른다.
- 주문은 UUID v4, 생산 회차·장비 명령·검사는 각각 별도 UUID를 사용한다. 실물 QR은 PALLET-01~08이다. 서버와 장비는 명령 ID로 접수 결과를 조회하고 같은 동작의 중복 실행을 막는다.

### 11. 명령 완료와 장애 복구

**질문:** 서버가 명령을 보냈는데 응답이 끊기면 무엇을 보고 재개할까요?

**팀 답변 — 장애 복구 원칙 확정**

- 명령 전송 후 응답이 끊기면 장비 상태를 먼저 조회한다. 응답이 없다는 이유만으로 동일 실물 동작을 다시 실행하지 않는다.
- 팔레트 배출·로봇팔 파지·AGV 하역 등이 실제로 끝났는지 확인할 수 없으면 작업자가 현장을 확인한 뒤 재개한다.
- 재개 전에 현재 장비 상태와 해당 주문·생산 회차·명령의 처리 상태를 대조한다. 명령 중복 실행 방지는 10번 원칙을 따른다.
- v0.1.0의 명령 상태·장비 상태 조회와 현장 확인 기록을 사용한다. 재부팅 후 기존 명령의 결과를 확인하기 전에는 배출·파지·하역을 다시 시작하지 않는다.
- 접수 제한시간·하트비트·장비별 동작 완료 제한시간·WPF 갱신 주기의 최종 수치는 미정이며 실제 환경에서 확인해 정한다. 현재 AGV 시험 코드의 500ms 하트비트·2초 만료 정지는 최종 팀 통신 규약으로 확정된 수치가 아니다.

### 12. 오류와 이력

**질문:** 문제가 생겼을 때 WPF와 로그에서 어떤 정보까지 한 번에 찾을 수 있어야 하나요?

**팀 답변 — 기록·조회 요구사항 확정**

- 오류 코드·내용, 발생 장비, 공정 단계, 관련 작업번호(주문·생산 회차·장비 명령 등), 발생 시각, 마지막 정상 상태, 가능한 조치 방법을 기록하고 관리자 화면에서 확인할 수 있게 한다.
- 주문번호를 기준으로 QR 배정 내역, 검사 사진·결과, 하역 이력을 연결해 조회할 수 있게 한다.

### 13. 기구와 센서

**질문:** 팔레트 배출·벨트 정차·액추에이터 끝 위치를 각각 무엇으로 확인할 수 있나요?

**팀 답변 — 현재 시험 코드 기준, 최종 실측값은 별도**

`firmware/RobotWorkSimulation/RobotWorkSimulation.ino` 및 `배선_참고.txt`에서 확인했다.

| 기능 | UNO 핀 | 현재 코드 동작 |
| --- | --- | --- |
| 컨베이어 펄스 | D5 | STEP/PUL 출력, 정지 시 HIGH 유지 |
| 컨베이어 방향 | D6 | DIR HIGH 고정, 실제 이송 방향은 배선·설치 상태로 확인 |
| 액추에이터 구동 허용·PWM | D9 | L298N ENA, 구동 255 / 정지 0 |
| 액추에이터 방향 | D7·D8 | 전진 HIGH·LOW / 복귀 LOW·HIGH / 정지 LOW·LOW |
| 첫 IR 센서 | D4 | INPUT_PULLUP, LOW 감지 / HIGH 통로 비움 |
| 두 번째 IR 센서 | D2 | INPUT_PULLUP, LOW 감지 / HIGH 통로 비움 |

- IR1·IR2 모두 20ms 동안 안정된 값을 확인한다. 현재 코드의 `ir_clear=true`, `ir2_clear=true`는 감지 중이 아니라 통로가 비었다는 뜻이다.
- 초기화 시 컨베이어 펄스를 정지 상태로 두고 액추에이터 PWM과 방향 출력을 끈다. 자동 운전은 `a` 명령과 시작 조건 확인 뒤 진행한다.
- 현재 시험 순서: 액추에이터 10초 전진 → 0.5초 대기 → 10초 복귀와 벨트 동시 시작 → IR1 감지 후 기본 5.5초 추가 이송 → 벨트 3초 정지(로봇팔 작업 가정) → 벨트 재구동 → IR2 감지 후 기본 2초 추가 이송 → 최종 정지. 벨트 최종 정지와 복귀 타이머가 모두 끝나야 회차 종료 응답을 보낸다.
- IR1·IR2를 감지한 즉시 벨트를 멈추는 코드는 아니다. 최종적으로 조립·인수 위치에 맞게 추가 구동 시간을 실측·조정해야 한다.
- 액추에이터는 끝 위치 감지가 아닌 타이머로 완료를 판단한다. 코드의 전진·복귀 값은 각각 10초지만, 사용자가 답변한 **최종 시간은 실측 후 확정**을 유지한다. `POSITION_UNVERIFIED` 응답도 실제 끝 위치 확인이 없음을 나타낸다.
- 컨베이어 펄스 반주기는 80μs이며 벨트가 계속 구동 중이면 30초 제한에서 양쪽 구동을 정지한다. IR 지연값이 크면 목표 지점보다 시간 제한이 먼저 적용될 수 있다.
- UI 조정 가능 시험값은 IR1 지연·로봇 작업 가정 대기·IR2 지연의 세 가지이다. 회차 도중 변경을 막고 UNO 재부팅 시 기본값으로 돌아간다.
- 모의 3초 대기는 실제 로봇팔 완료 신호를 대신한 시험용이다. 최종 공정에서는 조립 완료 및 대기 자세 확인 후 벨트를 재구동해야 하므로 완료 통신으로 교체해야 한다.
- 조립을 용이하게 하기 위해 모든 조립에 자석을 사용한다. 머리·팔과 몸통의 결합 및 몸통을 팔레트에 고정하는 부분에도 자석을 사용한다고 사용자가 확인했다.
- 팔레트 위 로봇의 배쪽이 로봇팔의 반대쪽을 향하도록 배치한다.
- 포크 단차·허용 하중: 사용자가 별도 기준 없음으로 답변했다. 수치 규격이나 실측 결과는 제시되지 않았다.
- 팔레트 치수는 가로 6 × 세로 6 × 두께 2cm, 즉 60 × 60 × 20mm이다(사용자 확인). 첨부 코드상의 핀·센서·출력 값은 앞의 표에 정리했으며 현재 물리 배선까지 현장에서 대조한 것은 아니다.

### 14. 로봇 좌표와 보정

**질문:** 작업 좌표의 원점·방향과 ‘집게가 도착했다’는 기준은 무엇으로 할까요?

### 16. YOLO와 암실 검사

**질문:** 정상·오부품·누락·가림을 어떤 영상 기준으로 구별하고, 누가 라벨을 검수할까요?

- 구매 웹·DB·YOLO의 공통 라벨 명칭은 02번에서 결정한 H1/H2/L1/L2/L3/R1/R2/R3을 사용한다. 이는 명칭 결정이며 데이터셋·모델에 반영 완료된 상태는 아니다.
- 암실 카메라 3과 링조명 아래에서 QR로 조회한 주문 사양과 부품 검출 결과를 대조한다는 목표 공정은 유지한다.

### 17. AGV 인수·하역

**질문:** AGV가 인수 위치에 바르게 정차했는지, 실제 팔레트 적재·하역이 됐는지 무엇으로 확인하나요?

**팀 답변 — 서보 동작 완료 기준**

- AGV 지게에는 팔레트 적재·하역 여부를 확인하는 별도 센서가 없다.
- 지게 서보의 동작 완료를 기준으로 인수·하역 완료를 판단한다. 실제 물체 감지나 서보 각도 실측 피드백으로 성공을 확인하는 방식은 아니다.
- 기존 공정대로 2번에서 85도로 대기하고 1번에서 110도로 올려 인수하며, 목적지에서 60도로 내려 하역한다. 최종 2번 복귀 후 85도로 돌아간다.
- 경로 정차는 라인트레이싱 센서 기반 기존 AGV 로직을 따른다. 지게의 완료 상태와 실제 팔레트 상태가 불명확하면 11번의 현장 확인 후 재개 원칙을 적용한다.
- 라인 이탈·저전압·암실 사용 불가의 상세 감지·정지 조건과 개별 현장 복구 담당은 미정이다. 전체 정지는 18번, 공통 통합·시험 담당은 23번을 따른다.

### 18. 제어권과 정지 범위

**질문:** WPF의 컨베이어 정지·공정 일시정지·현장 비상정지는 각각 어느 장비에 어떻게 적용하나요?

**팀 답변 — 전체 정지·해제 동작 확정, 물리 비상정지 구현 예정**

- 관리자 화면의 전체 공정 정지는 컨베이어·액추에이터·로봇팔·AGV를 모두 정지시키는 요구사항으로 확정한다.
- 서버가 각 장비에 정지를 전달하고 정지 상태를 확인하는 통합 제어가 필요하다. 이번 문답에서 모든 장비의 동시 정지 구현·실차 검증을 완료한 것은 아니다.
- 통신 응답이 끊기거나 완료 상태가 불명확하면 장비 상태와 실물을 확인한 뒤 재개하는 11번 원칙을 따른다.
- 사용자는 정지 해제 시까지 모든 공정을 정지한다고 확인했다. 전체 정지는 해제 조작이 있기 전까지 유지하며 공정이 자동으로 진행되지 않게 한다.
- 정상 운전 중 사용자가 전체 공정을 정지했다가 해제하면, 별도 시작 버튼 없이 멈췄던 공정을 바로 재개한다.
- 이를 위해 중단 공정·장비 상태와 필요한 타이머 진행 정보를 보존하는 정지/재개 처리가 필요하다. 첨부 UNO 시험 코드의 s 명령은 진행 순서를 취소하고 IDLE로 돌아가므로 이 요구사항을 그대로 충족하지 않으며 통합 시 수정·검증해야 한다.
- 통신 단절·장비 오류 등으로 실제 상태가 불명확한 경우는 11번의 상태 조회·현장 확인 후 재개 원칙을 유지한다. 정지 해제 요구를 불명확한 동작의 무조건 재전송으로 해석하지 않는다.
- 현장에 직접 누르는 물리 비상정지 버튼은 구현 예정이다. 실제 설치·배선·차단 범위·정지 확인 신호 및 물리 비상정지 복구 절차는 구현 단계에서 확정·검증한다. 관리자 화면의 정지 해제 동작과 동일하게 구현되었다고 간주하지 않는다.

### 19. 관리자 권한과 화면

**질문:** 재검 승인·수동 정비·설정 변경·로그 열람 권한은 누구에게 주고, WPF가 끊기면 무엇을 보여줄까요?

**팀 답변 — 관리자 권한·단절 처리·화면 기준 확정**

- 구매 웹은 소비자용이다. 04번에서 확정한 대로 소비자 로그인 없이 본인 주문번호로 조회하는 방침을 유지한다.
- WPF는 로그인 계정에 따라 1차 관리자·최상위 관리자로 권한을 구분한다. 별도 작업자 로그인 등급은 두지 않는다.
- 두 등급 모두 WPF에서 주문 수락, 팔레트 배출 전 생산 대기 주문 취소, 설비 정지·재시작을 수행할 수 있다.
- 관리자 계정 생성·등급 변경은 최상위 관리자 권한이다.
- 재검·재조립 기능은 06번에서 이번 구현 범위에서 제외했다.
- 최상위 관리자 전용 기능은 다음과 같다.

### 22. 합격 기준

**질문:** 최종 시연에서 어떤 수치와 시나리오를 통과해야 완료인가요?

**팀 답변 — 경로·예외 시험 각 3회, 정량 목표 미정**

- 여기서 합격 기준은 프로젝트의 정상 동작을 확인하기 위한 팀 자체 시험 기준이다.
- 정상 배송 3개 HUB(서울 3번·평택 4번·수원 5번)와 오류 구역 2개(6번·7번)에서 주문 → 조립 → 검사 → 하역 → AGV 복귀의 전체 공정이 경로별 3회씩 성공하는 것을 기본 기준으로 한다.
- 기본 배송·분류 시험은 5개 경로 × 3회 = 총 15회다. 연속 성공 조건을 추가로 확정한 것은 아니다.
- 성공은 주문·검사 결과에 맞는 목적지로 이송하고 하역한 뒤 AGV가 2번 정차·지게 85도 복귀까지 완료한 경우로 본다. 이는 기존 확정 최종 복귀 조건을 따른다.
- 이는 목표 시험 계획이며 실제 시험 완료·성공 횟수를 보고한 것이 아니다.
- YOLO 정확도·조립 성공률·처리시간·정차 오차의 목표 수치는 미정으로 확인했다. 기존 문서의 예시·초안 수치를 현재 확정 목표로 간주하지 않는다.
- 예외 시험은 QR 판독 실패, DB 저장 실패, 통신 단절·복구, 같은 명령 중복 수신, AGV 최종 복귀 전 다음 팔레트 배출 차단의 5종을 각각 3회씩 수행한다.
- 예외 시험은 각 상황에서 정해진 차단·알림·복구·중복 방지 동작이 정상적으로 이루어지는지 확인한다. QR 재판독 횟수와 예외 시험 반복 횟수는 별개이다.
- 기본 경로 15회와 예외 시험 15회를 합쳐 총 30회 시험 계획이다. 실제 수행 결과를 기재한 것은 아니다.
- 시험·측정 담당은 23번의 담당 배정에서 정리한다.

### 23. 담당자와 변경 승인

**질문:** 기존 파트 분담 외에 서버 공정 순서, Pi↔UNO 연결, QR 판독, 실물 통합 시험, 최종 시연은 각각 누가 맡나요?

**팀 답변 — 팀 공동 협의·이해준 통합 주도·천은상 GitHub 공유**

- 서버에서 주문 → 조립 → 검사 → 배송의 공정 실행 순서를 구성·관리하는 작업은 팀 전체가 함께 참여하고, 이해준이 주도한다.
- DB 테이블 구조·변경 관리와 DB 백업·복원은 기존 답변대로 최종현·함동윤이 담당하며 앱·장비 코드 배포·이전 버전 복귀는 각 파트 담당자가 맡는다.
- Pi↔UNO·QR 통합 연결, 전체 실물 통합 시험, 최종 시연도 팀 전체가 함께 참여하고 이해준이 주도한다.
- 개별 파트 구현·배포·이전 버전 복귀는 기존 파트 담당자가 맡으며, 위 공통 통합 업무의 주도 역할과 구분한다.
- 통신 규약·핀·좌표·판정 기준 등 공통 변경 사항은 팀 전체가 협의한다.
- GitHub에 변경 사항을 등록·공유하는 담당자는 천은상이다.
- 이해준의 통합 주도, 팀 전체의 변경 협의, 천은상의 GitHub 공유 역할을 구분한다.
- 별도의 대체 주도 담당자는 현재 확인되지 않았다.

- **통신 실측·배포:** v0.2.0의 메시지·인증·완료 규칙을 기준으로 구현하고, 포트·인증서 등 배포 설정과 장비별 하트비트·제한시간을 확정한다.

- **운영 세부:** 실제 계정·인증 연동, 결산 집계 기준, 재시작 후 로그인 유지, 보관 종료 시 삭제 방식, 환경 설정·백업 주기/위치·버전 기록 방식.
